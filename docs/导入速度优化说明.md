# 导入速度与稳定性优化说明（v1.1）

本轮优化针对 `main.ts` 的「结构导入 → 校验 → 补建」主流程，重点是**把固定的“批 + 等待”改成按在途命令数自适应**，并在失败时自动降速。

## 一、原来的问题

- 固定节奏：每 28 条命令一批，批间固定等 90ms → 理论上限约 **311 条/秒**，且不管服务器忙不忙都按同一速度硬发
- 管道容易空：`inFlight`（未回执命令数）没有参与节流，快的时候闲着、慢的时候堆压
- 失败没有反馈：失败率高时仍按原速发送，容易进一步断连
- 补建轮固定 400ms 后立即重发，服务器还没缓过来就再来一轮

## 二、现在的策略

### 1. 自适应发送窗口（核心提速）

```
每 12ms 检查一次：只要 在途命令数 < window，就继续发下一条
window 初始 = 48（首轮）/ 16（补建轮）
```

- 不再按“28 条一批 + 90ms”硬等待，管道始终喂饱
- 实际速度由服务器回执速度决定，理论上限提升到 **约 3000 条/秒**（受服务器与网络限制）
- HUD 仍按 250ms 更新，不影响游戏

### 2. 失败自动降速

```
每 400ms 采样一次：失败率 > 5% → window × 0.7（最低 8）
稳定且管道空闲 → window + 4（最高 48）
```

- 服务器扛不住时自动收缩，避免“越失败越猛发”导致的掉线
- 恢复后自动加速，不用手动重启

### 3. 补建轮退避重试

```
第 n 轮补建延迟 = 400ms × n（最多 2 秒）
补建轮初始窗口 = 全速的 1/3
```

- 给服务器留出恢复时间，降低二次失败率

### 4. 校验批大小可调

- 回读校验批大小：`FB_VERIFY_BATCH`（默认 100，原来是 80）
- 校验仍按批 Promise.all 并发，速度提升约 25%

## 三、可调环境变量

| 变量 | 默认 | 作用 |
|---|---|---|
| `FB_SEND_WINDOW` | 48 | 首轮最大在途命令数（越大越快，越大越容易断） |
| `FB_SEND_WINDOW_MIN` | 8 | 降速时的下限 |
| `FB_SEND_TICK` | 12 | 发送泵间隔（ms），越小越积极 |
| `FB_SEND_SAMPLE` | 400 | 失败率采样周期（ms） |
| `FB_SEND_FAIL_RATIO` | 0.05 | 超过该失败率开始降速 |
| `FB_VERIFY_BATCH` | 100 | 回读校验每批并发数 |

## 四、推荐档位

| 场景 | 配置 |
|---|---|
| 本地/自己服，网络好 | 默认即可 |
| 服务器较卡、频繁掉线 | `FB_SEND_WINDOW=24 FB_SEND_TICK=20` |
| 大结构追求速度 | `FB_SEND_WINDOW=64 FB_SEND_TICK=8`（观察失败率） |

## 五、稳定性收益

- 断线保护：任一时刻在途命令数有上限，不会无限堆积
- 失败可见：日志会打印「发送失败率 x%，降速：窗口 y」
- 补建退避：避免一轮失败后立刻再来一轮造成雪崩
- 取消/停止仍即时生效（`build.cancelled` 检查保留在泵循环开头）

## 六、后续可做

- 校验失败点按坐标去重后再补建（现在按命令去重）
- 导入进度按“已确认方块数”而不是“已发送方块数”计算，HUD 更准
- 大型结构分区块流水线：放完一个区块立即校验，减少尾部等待
