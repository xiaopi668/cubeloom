# Cubeloom 维护手册

> 面向接手维护的人。分析基线：2026-11-08，`main` @ `1284db0`，Node 26.13.0 / npm 12.2.2 / tsx 4.23.15（Linux）。
> 深度报告原件在 [`docs/analysis/`](analysis/README.md)（core / formats / surface 三份，合计 1800 行，全部带 `file:line`）。

## 0. 一页速览

- **是什么**：一个跑在本地的 WebSocket 服务，替玩家在《我的世界》基岩版里一块块放方块；支持结构文件导入、聊天栏 JS 现场造型（VoxelGeometry）、MIDI 音乐盒、像素画/像素字、网易版指令桥。
- **规模**：源码 ~8100 行（`main.ts` 1599 / `admin-server.ts` 1152 / `src/*` 2574 / `admin/*` 前端 ~2600 / `cli.mjs` 299）；无构建步骤，`tsx` 直接跑 TS。
- **许可**：AGPL-3.0-or-later，fork 自 MIT 的 CyanQiuper-Builder 并剥离全部商业模块。
- **健康度**：自测 39/39 通过、启动冒烟通过；但**这 39 条断言覆盖不到最危险的几个 P0**（详见 §6）。
- **接手第一件事**：读 §6 P0，按 §11 的规则改；不要在没有真机回执环境的情况下"优化"导入链路。

```bash
npm ci                              # 安装（tsx/ws 已是生产依赖，--omit=dev 也能跑）
npm run check:sandbox               # 39 项自测
FB_NO_OPEN=1 npm run admin          # 面板 http://127.0.0.1:11452（会拉起 WS:11451）
npm run ws                          # 只起 WS（调试命令流）
```

## 1. 项目定位与边界

| 是 | 不是 |
|---|---|

上游关系：`Diamond-Minec/CyanQiuper-Builder (MIT)` → 剥离商业模块 → `xiaopi668/cubeloom (AGPL-3.0-or-later)`。署名义务写在 `NOTICE`、`LICENSES/CyanQiuper-MIT.txt`。

## 2. 进程与端口

```
                         ┌─────────────────────────────┐
 浏览器 ──HTTP 11452 ──> │ admin-server.ts             │
                         │  · 静态页 + /api/*          │
                         │  · SSE 跟 logs/*.log        │
                         │  · spawn/kill main.ts       │
                         └───────────┬─────────────────┘
                                     │ HTTP 127.0.0.1:11453
                                     ▼
 玩家 ──/connect ws 11451 ──> ┌─────────────────────────────┐
                             │ main.ts                     │
                             │  · WS 会话 / --login 认证    │
                             │  · 沙箱 / 结构导入 / HUD     │
                             │  · 控制接口 11453(回环)      │
                             │  · Java 通道 11454(默认关)   │
                             └───────────┬─────────────────┘
                                         │ 原版命令流
                                         ▼
                                    游戏服务器
```

| 端口 | 谁在听 | 默认绑定 | 说明 |
|---|---|---|---|
| 11451 | `main.ts` | `0.0.0.0` / `::`（通配） | 玩家 `/connect` 进来；外部来源必须 `--login` |
| 11453 | `main.ts` | `127.0.0.1` | 控制接口（`/eval`、`/send`、`/structure/*`），面板与 CLI 用 |
| 11452 | `admin-server.ts` | `127.0.0.1`（`FB_ADMIN_HOST` 可改） | 面板；**绑 0.0.0.0 前必须先设口令** |
| 11454 | `netease-service.ts` | `127.0.0.1` | 网易版桥（可选）；`main.ts` 的 Java 通道默认关闭，两者同开会撞端口 |

进程关系：`admin-server.ts` 用 `spawn` 拉起 `main.ts`（POSIX 建进程组、Windows 用 `taskkill`），面板退出时尽力杀掉子进程；WS 服务也可以完全独立启动，此时面板只监控不拥有。

## 3. 三条主链路

### A. 聊天栏命令 → 沙箱 → 落块

```
游戏聊天 "-plot(sphere(3,0))"
  → Session.handleChat()             src/session.ts
  → Sandbox.eval(code)               src/sandbox.ts（node:vm 新 context，默认 5s 超时）
  → 注入的 plot()/setBlocks()        src/session.ts + src/effect.ts
  → 逐条 sendCommand("setblock …")   无窗口限制，同步灌入
  → 回显 tell_raw / actionbar        src/utils.ts
```

承重点：`sandbox.ts` 每次执行新建 context（顶层 `const` 不冲突）；`effect.ts` 的 `setBlocks` 逐块发命令、`count` 语义同时驱动统计与 HUD。

### B. 结构文件 → 解析 → 命令流 → 回读 → 补建

```
上传(面板/CLI) → POST /structure/prepare
  → parseStructureFile(buf, name)        src/formats.ts（按魔数/扩展名分派 5 种格式）
  → ParsedStructure { blocks, size, palette }   src/structure.ts
  → structureCommands(st, origin, offsetY)      → setblock / fill（同轴连续 64 格合并）
  → sendBatch()：inFlight 窗口 + 失败降速 + 最多 N 轮补建   main.ts
  → verifyStructure()：surfaceSamplePoints → testforblock 抽查 → setblock 补 → 复检
  → HUD（actionbar）+ 日志（logs/ws.log）
```

强制三步流水线在面板里是 `prepare → build → verify`；`build` 失败的命令进入 `lastFailed`，由 `/structure/rebuild` 补建。

### C. 面板 / CLI → 控制口

```
面板 fetch /api/*  ──> admin-server（口令 Cookie 可选）──> http://127.0.0.1:11453/*
CLI   fetch /eval  ─────────────────────────────────────> 同上
```

控制口本身**没有鉴权**，靠"只绑回环 + 请求守卫"兜底（2026-11-08 加：`application/json` 强校验、`Origin` 同源、`Host` 必须回环）。

## 6. 风险登记册

> 状态：`已修` = 本轮已改并验证；`已缓解` = 加了防线但根因仍在；`开放` = 未处理。
> 标注 ✅ 的是我本人复核过的（读码或实测），◐ 的是分析报告结论、未独立复现（原件见 `docs/analysis/`）。

### P0（能远程执行代码 / 静默毁数据 / 生产跑不起来）

**P0-1 沙箱逃逸 = 宿主 RCE**｜✅ 实测｜**开放**
`src/sandbox.ts:46-62` 的 `codeGeneration.strings:false` 只封了**新 realm** 的 `Function`；注入的 `plot` / `setBlocks` / `session` 都是宿主对象，它们的 `constructor` 是宿主 `Function`：

```
plot.constructor('return process')().version                        → v26.13.0
plot.constructor('return process')().getBuiltinModule('child_process').execSync('id')  → 执行成功
```

`tools/check-sandbox.ts:57-68` 恰好只测了 `Function('return process')` 这条最短路径，所以 39/39 全绿。
影响：**能发 `-` 命令或能调控制口 ⇔ 能在宿主上执行任意代码**（以服务进程身份）。
根治：把执行搬进 `worker_threads`/子进程，只回传方块数据；在那之前，README/文档必须继续把它说成"玩法"而不是"隔离"。

**P0-2 控制口与面板的远程可达面**｜✅ 实测｜**已缓解**
- 控制口 `/eval` 原来不校验 `Content-Type` / `Origin` / `Host`：`text/plain` + `Origin: evil.example` 直接进执行分支（✅ 实测）；
- 面板 `admin/auth.json` 不存在时**完全无鉴权**（fail-open），而 `start.sh` 原来把面板绑到 `0.0.0.0`；实测局域网 IP 可 `GET /` 200、`POST /api/command` 被受理（✅ 实测）。
- 本轮修复：两个服务都加 `requestGuard`（写操作必须是 `application/json`；`Origin` 必须与 `Host` 同源；`Host` 必须回环/本机 IP 字面量）；`start.sh` 默认改绑 `127.0.0.1`。
- 仍开放：控制口本身无令牌；面板口令默认不存在；DNS rebinding 只靠 Host 白名单挡。

**P0-3 生产安装跑不起来**｜✅ 实测｜**已修**
`tsx`（所有启动路径都依赖它）原来在 `devDependencies`，`ws` 被 `main.ts` 直接 import 却完全没声明。`npm ci --omit=dev` 后 `node_modules/tsx` 缺失，`start.sh` / systemd / Windows bat 全挂。
本轮：`tsx`、`ws` 移入 `dependencies`，`npm ci --omit=dev` 实测可启动。

**P0-4 「损坏修补」会静默破坏规范文件**｜✅ 实测｜**已修**
原实现（`src/structure-repair.ts:160-200`）重建 root 时只保留 `format_version / size / block_indices / palette{default}`：
`entities` 写死 `[]`（:173）、`block_position_data` 写死 `{}`、方块状态（`states`）与多余调色板层全部丢失；
面板 (`admin/index.html:913`) 还对 `fixed=false` 的文件显示"文件本来就规范，无需修补"，同时给出下载按钮——用户以为拿到的是副本，实际是**降级版**。

修复（本轮）：
- 新增带类型的 NBT AST（`parseNbtTyped` / `serializeNbt` 支持全部 12 种标签），修补改为**在 AST 上改字段**，不认识的键、`states`、`entities`、`block_position_data` 原样写回；
- 文件本来就规范且无 gzip 时**直接返回原始字节**（实测逐字节相同），不再重写；
- `RepairResult` 增加 `lossy`，面板遇到有损修复会显式警告；`fixed=false` 的文案改为"下载的副本与原件一致"；
- 修补接口不再拒绝 gzip（修补器本来就会解压；原来 `main.ts` 的入口判断和实现互相矛盾）。

### P2（清理项，按需处理）

- 死代码：`main.ts` 的 `actionbarText` / `sendActionbar` 无调用；`parseMcStructure` import 未用；`effect.ts` 的 `setBlock`/`overSpace` 仅测试用；`netease-*` 的 `runBatches` / `bridgeError` / `bridgeConnected` / `VERIFY_CONCURRENCY` 未使用。
- 前端：`snowluma.css`(11.8K)、`polish.css`(11.4K) 未被任何页面 `<link>`，却仍可被公开访问；三套 CSS 选择器大量重叠；`.progress` / `.log-list .row` 等类名与 JS 生成的不一致，进度条不可见。

## 9. 发布与合规

- **AGPL §13**：网络服务必须提供"对应源码"的获取方式。当前**完全没有**：面板没有 `/source` 路由、页面没有链接。最小合规做法：面板页脚加仓库链接 + 在 `/api/status` 返回 `sourceUrl`，并在 `ADMIN.md` 写清"修改版必须同样开放源码"。

- **依赖许可**：`@pureeval/voxel-geometry@1.2.10` 的 npm 元数据没有 `license` 字段、包内无 LICENSE，npm `license` 只能靠上游仓库证明——建议锁版本时在 `NOTICE` 注明 commit 与取证日期；`mcpews`/`ws` 为 MIT；`tsx` 为 MIT（现在是生产依赖，应补进 `NOTICE`）。
- **SPDX 一致性**：`package.json` 写 `AGPL-3.0-or-later`，README 徽章写 `AGPL-3.0`，`NOTICE` 写"第 3 版或任何更新版本"——统一成 `AGPL-3.0-or-later`。

## 10. 运维与故障排查

```bash
# 启动（面板 + WS）
./start.sh                 # 或 npm run admin；Windows 双击 start.bat
# 只启动 WS
npm run ws
# 固定外部连接令牌
FB_LOCAL_TOKEN=mysecret npm run ws
# 改端口（并行多实例调试）
FB_WS_PORT=11461 FB_CONTROL_PORT=11463 FB_ADMIN_PORT=11462 FB_NO_OPEN=1 npm run admin
# 面板口令
printf '%s' '新口令' | node tools/set-password.mjs --stdin
```

| 现象 | 先查 | 处理 |
|---|---|---|
| 游戏 `/connect` 无反应 | `logs/ws.log` 是否有"WS 服务已启动"；端口是否被占 | 换 `FB_WS_PORT`；确认协议版本 `FB_WS_VERSION` 与客户端匹配 |
| 连上但命令没反应 | 是否发过 `--login <令牌>`；`/status` 里 `authenticatedSessionCount` | 令牌见启动日志；本机连接本应免验证 |
| 面板"未验证身份" | `GET :11453/status` 的 `sessions` | 重启 WS；旧版会有幽灵会话占位（P1-6） |
| 导入卡在某个百分比 | `build.sent` / `build.confirmed` / `build.retryRound` | 先 `/structure/cancel`，再降窗口：`FB_SEND_WINDOW=24` |
| 导入"完成"但方块缺失 | 回读只比块名、不比对 states（P1-7） | 用深度校验 `/structure/verify?deep=1`，或看 `failedBlocks` |
| 面板 401 | `admin/auth.json` 是否存在/损坏 | 删除即免登录；重新 `set-password` |
| 端口被占 | `ss -ltnp \| grep 1145` | 改端口；先 `stop.bat`/`pkill` |
| 日志不更新 | 面板读 `<repo>/logs`，WS 可能被 `FB_LOG_DIR` 指到别处 | 统一 `FB_LOG_DIR` 或看绝对路径 |

## 11. 维护者规则

1. **不主动 commit/push**：改动留在工作区，由维护者 review 后自行提交（本仓库当前工作区含本轮未提交改动）。
2. **改前跑测**：`npm run check:sandbox`（39 条）；改 `main.ts` 导入链路再加启动冒烟；改面板加一次 `GET /` + `GET /api/status`。
3. **坐标契约只加一次**：`structureCommands` 产出的命令已含 `origin + offsetY`，任何补建/复检/重发都直接用命令或 `world(p)`，不要再叠加。
4. **鉴权顺序不能换**：`--login` 必须在消息分派前处理；`resolveRequireAuth` / `isLoopback` 是唯一判据。
5. **不要给沙箱"加保险"当安全修复**：真正隔离只有进程/线程边界；在此之前，任何"沙箱已隔离"的文案都是误导。
6. **许可证相关改动**（依赖、署名、SPDX）必须在 PR 描述里说明理由，并同步 `NOTICE`。
7. 文档改动以代码为准：`README`/`ADMIN`/`DEV` 里的端口、断言数、脚本名都曾被写错一次，改完顺手 grep 一遍。
